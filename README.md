Real-Time Driver-to-Request Dispatch Matching Service
Status: Day 1 — Initial Architecture Submission
Implementation Status: Architecture and design phase. Application code will be implemented during the remaining training period.
1. Overview
A backend dispatch service for a ride-hailing/delivery platform that matches incoming requests to the most suitable available driver in near-real-time.
The system is designed around a key observation: this is not simply a "find the nearest driver" problem. Driver availability changes continuously, driver locations can be slightly stale, multiple requests may compete for the same driver, and a driver may disappear after being selected.
The primary engineering goals are therefore:
•	Prevent double-assignment under concurrent requests.
•	Make reasonable decisions using potentially stale driver locations.
•	Select drivers using ETA and traffic-aware information rather than distance alone.
•	Automatically recover when a reserved driver fails to confirm.
•	Maintain good matching quality without introducing unnecessary matching latency.

2. Key Assumptions
The following are configurable project assumptions rather than universal industry standards.
Location freshness
Location age	Classification	Matching behavior
< 10 seconds	FRESH	Normal eligibility
10–30 seconds	SLIGHTLY_STALE	Eligible with ranking penalty
> 30 seconds	TOO_STALE	Normally excluded
The system does not require perfectly fresh GPS information. Instead, location freshness becomes a confidence factor in the matching decision.
Assignment confirmation
A driver has 15 seconds to confirm an assignment after being reserved.
This value is intentionally short for demonstration and testing purposes and will be configurable through application configuration.
Candidate shortlist
Matching is performed in two stages:
1.	Cheap geographic filtering identifies approximately 5–8 nearest eligible drivers.
2.	More expensive ETA/traffic scoring is performed only on this shortlist.
The shortlist size is configurable.
Traffic and ETA
A RoutingService abstraction will provide ETA and traffic information.
The initial implementation will use a deterministic mock routing service with simulated traffic conditions such as:
LOW       → 1.0× travel-time factor
MODERATE  → 1.25×
HIGH      → 1.6×
The project will not scrape Google Maps traffic visualization. The routing abstraction allows a real traffic-aware provider to be integrated later without changing the dispatch engine.
Driver simulation
Drivers and their location updates will be generated by a standalone simulator rather than real GPS/mobile clients, as permitted by the project brief.
Deployment
The initial implementation assumes:
•	Single region
•	One Spring Boot application
•	One PostgreSQL database
•	No distributed locking
•	No geo-sharding
This keeps the concurrency model simple enough to reason about and test within the project timeframe.

3. Matching Strategy
The dispatch engine uses a two-stage matching pipeline.
Request arrives
      ↓
Find AVAILABLE drivers
      ↓
Vehicle / eligibility filtering
      ↓
Location freshness filtering
      ↓
Geographic shortlist
      ↓
ETA + traffic calculation
      ↓
Request scarcity + waiting-time scoring
      ↓
Rank candidates
      ↓
Atomic driver reservation
      ↓
Assignment confirmation
Stage 1 — Geographic filtering
The service performs inexpensive geographic filtering using driver coordinates and the request pickup location.
Haversine distance and/or a bounding-box filter can be used to identify nearby candidates.
Only the nearest approximately 5–8 eligible drivers proceed to the next stage.
Stage 2 — ETA-aware scoring
The shortlisted drivers are evaluated using:
•	Estimated arrival time
•	Traffic conditions
•	Distance
•	Location freshness
•	Vehicle compatibility
•	Request scarcity
•	Request waiting time
The goal is to avoid selecting a driver simply because they are geographically closest.
For example:
Driver A
Distance: 2 km
Traffic: HIGH
ETA: 14 min

Driver B
Distance: 3.5 km
Traffic: LOW
ETA: 8 min
Driver B may be preferable despite being farther away.

4. Request Scarcity-Aware Matching
An additional matching enhancement is request scarcity.
When multiple requests compete for the same driver, the system considers how many viable alternative drivers are available for each request.
Example:
Request A → 5 viable alternatives
Request B → 0 viable alternatives

             Driver D1
              /     \
             /       \
            A         B
If both requests compete for D1, Request B can receive higher priority because it has fewer practical alternatives.
This prevents the system from treating all requests as equally replaceable.
Request scarcity is a secondary matching policy. It never overrides the concurrency guarantee.
The scoring layer decides which request should receive priority. The database-level atomic claim decides whether the driver can actually be assigned.

5. Waiting-Time Protection
A request should not continuously lose to newer requests simply because another request has a slightly better score.
Therefore, waiting time can contribute a configurable priority boost:
Waiting time ↑
     ↓
Priority ↑
This provides basic starvation protection while keeping the scoring system simple enough to explain and test.

6. Concurrency Guarantee
The most important correctness requirement is:
Two simultaneous requests must never be assigned to the same driver.
A simple read-then-write implementation is unsafe:
Request A → SELECT Driver D1 → AVAILABLE
Request B → SELECT Driver D1 → AVAILABLE

Request A → UPDATE D1 → RESERVED
Request B → UPDATE D1 → RESERVED
Both requests can observe the same stale state.
The planned implementation instead uses an atomic conditional update:
UPDATE driver
SET status = 'RESERVED'
WHERE id = :driverId
AND status = 'AVAILABLE';
The application checks the affected-row count:
1 row affected → reservation succeeded
0 rows affected → driver was already claimed/changed
If the claim fails, the matching service proceeds to the next-ranked candidate.
This places the correctness guarantee at the database/transaction level rather than relying on application-side synchronization.

7. Driver Failure and Automatic Reassignment
A driver may disappear after being selected but before confirming.
The assignment lifecycle is:
AVAILABLE
    ↓
RESERVED
    ↓
ASSIGNMENT_SENT
    ↓
CONFIRMED
    ↓
BUSY
If confirmation does not arrive within the configured timeout:
ASSIGNMENT_SENT
       ↓
     TIMEOUT
       ↓
Release driver
       ↓
Requeue request
       ↓
Run matching again
The reassignment process is bounded by a configurable retry policy so that a request does not remain indefinitely in a pending state.
Late confirmation is handled safely using conditional state transitions so that a confirmation racing with timeout processing cannot resurrect an expired assignment.

8. API Overview
Update driver location
POST /drivers/{id}/location
Updates the driver's latitude, longitude, and location timestamp.
Update driver status
PATCH /drivers/{id}/status
Possible states include:
AVAILABLE
RESERVED
BUSY
OFFLINE
DISCONNECTED
Submit request
POST /requests
Creates a ride/delivery request and triggers the matching workflow.
Get request
GET /requests/{id}
Returns request state and assignment information.
Confirm assignment
POST /assignments/{id}/confirm
Allows the driver to confirm a reservation.
Detailed request/response schemas will be added during implementation.

13. Testing Strategy
The most important tests will use a real PostgreSQL environment through Testcontainers.
This is particularly important for the concurrency guarantee because an in-memory mock cannot reliably reproduce the database transaction behavior that protects driver claiming.
Planned test scenarios include:
Scenario	Expected result
One request + one driver	Driver assigned
Two requests + one driver	Only one receives driver
Two requests + two drivers	Requests receive different drivers
Concurrent matching	Same driver cannot be claimed twice
Fresh location	Normal ranking
Slightly stale location	Eligible with penalty
Too-stale location	Normally excluded
Farther driver with better ETA	Better ETA can win
High traffic route	ETA reflects traffic penalty
Scarce request	Receives priority when competing for a scarce driver
Long-waiting request	Waiting-time boost prevents starvation
Driver fails confirmation	Assignment times out
Timeout	Request is automatically rematched
Duplicate confirmation	No invalid state transition
Late confirmation after timeout	Cannot resurrect expired assignment
The concurrency test will use explicit thread coordination, such as CountDownLatch, to ensure that matching attempts genuinely overlap.

P1 — Deferred if time allows
•	Full simulator scenario library
•	WebSocket-based real-time updates
•	Minimal dispatch dashboard
•	Structured logging
•	Metrics/observability
•	More detailed API documentation
•	Production deployment configuration
P2 — Intentionally excluded
Real maps/traffic API
A real external routing provider introduces API keys, quotas, network failures, and external dependencies that are unnecessary for demonstrating the core dispatch problem.
The RoutingService abstraction allows a real provider to be added later without changing the matching engine.
Authentication
Not required by the project brief and would consume implementation time without contributing to dispatch correctness.
Payments
Outside the scope of driver/request matching.
Ratings as a product feature
A rating value may be used as a future ranking signal, but a complete ratings system is not required.
Surge pricing
Not part of the dispatch correctness problem.
Machine-learning ETA prediction
A deterministic routing abstraction is sufficient for demonstrating traffic-aware matching during the five-day implementation window.
Kafka / Kubernetes / Microservices
These introduce distributed-system complexity without a concrete requirement in the brief.
A modular monolith with one transactional PostgreSQL database provides a simpler and more defensible concurrency model for this project.
Real mobile clients
Synthetic driver simulation is sufficient for demonstrating frequent location changes, concurrency, and driver disappearance.
